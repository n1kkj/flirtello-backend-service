# Требования к Сервису Переводов с Персистентной Памятью (Translation Memory)

## 1. Обзор и Цель

Цель — расширить существующий сервис `Translator`, добавив ему функционал персистентной **"Памяти переводов" (Translation Memory, TM)**. Это превратит сервис из простого "прокси" к LLM в интеллектуальную систему кэширования и управления переводами.

Текущая реализация `InMemoryTranslationMemory` будет заменена на новую, которая использует базу данных для хранения, что предотвратит потерю накопленных переводов при перезапусках.

## 2. Ключевой флоу получения перевода

Сервис должен работать по следующему алгоритму:

1.  **Проверка кэша в памяти (L1):** Сначала сервис ищет перевод в локальном, быстром кэше в памяти (с коротким временем жизни). Если находит — немедленно возвращает.
2.  **Проверка Памяти переводов в БД (L2):** Если в L1 кэше нет, сервис ищет перевод в основной таблице `translations` в базе данных. Если находит — помещает его в L1 кэш и возвращает.
3.  **Обращение к LLM:** Если перевода нет и в базе, сервис вызывает внешний LLM для получения перевода.
4.  **Сохранение и возврат:** Новый перевод сохраняется и в **базу данных (L2)**, и в **кэш в памяти (L1)**, после чего возвращается пользователю.

## 3. Функциональные требования

### 3.1. Хранение переводов

*   **Персистентность:** Все переводы, полученные от LLM, должны сохраняться в специальной SQL-таблице `translations`.
*   **Структура записи:** Каждая запись в таблице должна содержать:
    *   Уникальный ключ для поиска.
    *   Язык перевода.
    *   Исходный текст (на английском).
    *   Переведенный текст.
    *   Флаг верификации (`is_verified_by_human`).
    *   Временные метки (`created_at`, `updated_at`).

### 3.2. Система идентификации (ключи)

*   Система должна поддерживать **гибридную систему ключей**:
    *   **Приоритет - Контекстный ключ:** Когда контекст известен (например, перевод поля `name` у персонажа с `id=123`), должен использоваться структурированный ключ вида `entity:id` (например, `character_name:123`). Это обеспечивает точность перевода.
    *   **Резерв - Текстовый ключ:** Когда контекст неизвестен или не важен (например, для статичных элементов UI), в качестве ключа должен использоваться сам исходный текст.

### 3.3. Workflow для редакторов (Верификация)

*   **Флаг верификации:** Все новые, автоматически сгенерированные переводы должны сохраняться в базу с флагом `is_verified_by_human = false`.
*   **Защита от перезаписи:** Сервис **не должен** пытаться заново перевести и обновить в базе запись, у которой флаг `is_verified_by_human` установлен в `true`. Это позволяет редакторам утверждать и исправлять переводы, не опасаясь, что их работа будет затерта автоматикой.

## 4. Нефункциональные требования

*   **Интеграция в архитектуру:** Новая реализация (`SQLTranslationMemory`) должна полностью соответствовать существующему интерфейсу `BaseTranslationMemory`, чтобы ее можно было "бесшовно" подменить в DI-контейнере без изменения бизнес-логики сервиса `Translator`.
*   **Производительность:** Таблица `translations` должна иметь индексы по ключевым полям (`key`, `language`) для быстрого поиска.
*   **Модульность:** Все, что относится к новой реализации (модели, миграции, код), должно находиться внутри модуля `src/translator/`.
*   **Изоляция данных:** Таблица `translations` должна находиться в отдельной схеме PostgreSQL с названием `translator`, чтобы изолировать данные сервиса от остальной части приложения.

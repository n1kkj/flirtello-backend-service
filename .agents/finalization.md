# Как правильно завершить задачу

Эта инструкция описывает шаги для документирования результатов работы после выполнения задачи.

## Обязательные шаги
### 0. Прочитайте из Asana MCP формулировку задачи.
### 1. Создайте `tasks/TASK-ID/TASK-ID-Result.md`

**Назначение:** Краткий результат выполненной работы для быстрого понимания "что было сделано".

**Структура:**

```markdown
# TASK-ID: Название задачи

## Задача

Краткое описание исходной задачи (1-2 предложения).

## Что сделано

### 1. Первое изменение
- Описание проблемы
- Решение

### 2. Второе изменение
- ...

## Верификация

✅ Как была проверена корректность
✅ Какие тесты прошли
✅ Что работает

## Отладка: Что искать в логах

**КРИТИЧНО:** Если в рамках задачи есть какая-то обработка ошибок и логирование, обязательно добавьте секцию о том, как искать в логах позитивные и негативные сценарии. Нужно описать, что за логирование было добавлено или изменено.

**Что включать:**
- Успешный сценарий: какие сообщения должны быть в логах при нормальной работе
- Fallback/частичный успех: что появляется при работе fallback механизмов
- Ошибки: какие сообщения указывают на проблемы
- Примеры запросов для поиска в логах (New Relic NRQL, grep, и т.д.)
- Ключевые индикаторы для быстрой диагностики

**Пример структуры:**
```markdown
## Отладка: Что искать в логах

### Успешный сценарий
В логах должно быть: `INFO - Success message`

### Fallback сценарий
В логах должно быть: `WARNING - Fallback activated`

### Ошибка
В логах будет: `ERROR - Error message`

### Поиск в New Relic
SELECT * FROM Log WHERE message LIKE '%pattern%' SINCE 24 HOURS AGO
```

## Результаты

Ключевые метрики или выводы (если применимо).

## Файлы изменены

- `path/to/file1.md` - краткое описание
- `path/to/file2.sql` - краткое описание

## Документация

Ссылки на Findings и обновленные руководства.
```

**Пример:** См. `tasks/AL-111/AL-111-Result.md`

### 2. Создайте `tasks/TASK-ID/TASK-ID-Findings.md`

**Назначение:** Технические находки и lessons learned для будущего использования.

**Что включать:**

1. **Технические проблемы**, которые были обнаружены
   - Ошибки в инфраструктуре (Evidence.dev, DuckDB, и т.д.)
   - Паттерны использования инструментов
   - Best practices

2. **Специфика проекта**, которая была обнаружена
   - Особенности данных
   - Бизнес-логика
   - Связи между таблицами

3. **Решения и workarounds**
   - Как обойти проблемы
   - Какие шаблоны использовать

**Структура:**

```markdown
# TASK-ID: Технические находки

## [Инструмент/Компонент]: Проблема 1

**Проблема:** Описание
**Решение:** Код или инструкция

## [Проект]: Специфика 1

**Что обнаружено:** ...
**Как использовать:** ...

## Выводы

Список ключевых принципов (numbered list).
```

**Пример:** См. `tasks/AL-111/AL-111-Findings.md`

### 3. Организуйте артефакты в `tasks/TASK-ID/artifacts/`

**Назначение:** Все вспомогательные файлы, созданные в процессе работы над задачей.

**Что складывать в `artifacts/`:**
- Скрипты для бенчмарков, тестирования, анализа
- Временные файлы с результатами (логи, CSV, JSON)
- Дополнительная документация (анализы, планы)
- Конфигурационные файлы для тестов (YAML, JSON)
- Любые другие файлы, созданные специально для этой задачи

**Структура:**
```
tasks/TASK-ID/
├── TASK-ID-Result.md
├── TASK-ID-Findings.md
└── artifacts/
    ├── benchmark_script.py
    ├── test_results.csv
    ├── analysis.md
    └── ...
```

**Правило:** В `artifacts/` идут **только файлы, созданные для этой задачи**. Код, который используется в продакшене, остается в обычной структуре проекта.

**Пример:** См. `tasks/AL-133/artifacts/` и `tasks/AL-134/artifacts/`

### 4. Обновите руководства (`.agents/*.md`)

**Если вы обнаружили новые patterns или best practices**, добавьте их в соответствующие руководства:

- **`.agents/dashboards.md`** - для дашбордов
- **`.agents/[другое].md`** - для других компонентов

**Правило:** В руководства идут **только общие patterns**, применимые к любым задачам. Специфичные детали проекта (например, названия таблиц биллинга) - в Findings.

**Что добавлять:**
- Новые workflow (например, "DuckDB → Дашборд")
- Распространенные ошибки и их решения
- Форматирование и синтаксис
- Инструменты и их использование

**Что НЕ добавлять:**
- Детали конкретной бизнес-логики
- Специфичные SQL запросы к конкретным таблицам
- Логику, специфичную только для одной задачи

- [ ] Создан `TASK-ID-Result.md` с кратким описанием
- [ ] Создан `TASK-ID-Findings.md` с техническими деталями
- [ ] Добавлена секция "Отладка: Что искать в логах" в Result.md (если применимо)
- [ ] Артефакты организованы в `tasks/TASK-ID/artifacts/` (если были созданы)
- [ ] Обновлены руководства `.agents/*.md` (если есть общие patterns)
- [ ] Код проверен и работает
- [ ] Критические метрики прошли cross-check (если применимо)

## Примеры

### Хороший Result.md ✅
- Краткий (≤ 50 строк, но может быть больше если есть секция про логи)
- Структурированный
- Содержит конкретные изменения
- Показывает результаты верификации
- Включает секцию "Отладка: Что искать в логах" (если применимо)

### Хороший Findings.md ✅
- Разделен по категориям (инструмент/проект)
- Содержит примеры кода
- Объясняет "почему", а не только "что"
- Завершается списком выводов

### Хороший Walkthrough.md ✅
- Начинается со скриншота результата
- Показывает проблемы и решения
- Краток, но информативен
- Отсылает к Findings для деталей

## Антипаттерны ❌

**НЕ делайте:**
- ❌ Дублируйте информацию между Result, Findings и Walkthrough
- ❌ Пишите длинные тексты в Result (детали → Findings)
- ❌ Добавляйте специфику проекта в `.agents/*.md` (это → Findings)
- ❌ Забывайте про скриншоты в Walkthrough
- ❌ Оставляйте невыполненные пункты в task.md

## Резюме

| Файл | Назначение | Размер |
|------|------------|--------|
| `Result.md` | Краткий итог | ≤ 50 строк |
| `Findings.md` | Технические детали | Любой |
| `artifacts/` | Вспомогательные файлы | Любой |
| `walkthrough.md` | Визуальная демонстрация | Средний |
| `.agents/*.md` | Общие patterns | Добавки |
| `task.md` | Чеклист | Завершить |

# Документация по процессу подбора и отправки изображений

Этот документ описывает различные рабочие процессы, которые приводят к подбору и отправке изображения пользователю. Понимание этих процессов имеет решающее значение для отладки и расширения функций, связанных с изображениями.

Система **не генерирует новые изображения** в реальном времени. Вместо этого она использует два основных технических пути для **интеллектуального подбора** наиболее подходящего изображения из существующей библиотеки:

1.  **Прямой подбор**: Выполняется специализированный вызов API с явной целью подобрать изображение. Используется эндпоинт `/illustrations/get_illustration`.
2.  **Неявный подбор**: Выполняется общий вызов к языковой модели (LLM) персонажа. LLM сама решает, ответить текстом или подобрать подходящее изображение. Используется эндпоинт `/chat/messages`.

---

## Сценарии, запускающие подбор изображений

1.  **Случайное изображение**: Изображение отправляется случайным образом каждые N сообщений в обычном чате.
2.  **Текстовый запрос**: Пользователь явно просит изображение в текстовом сообщении (например, "покажи свою фотографию").
3.  **Запрос по кнопке**: Пользователь нажимает кнопку, такую как "Get Image ❤️‍🔥".

---

## Детальный анализ процессов подбора

### 1. Процесс прямой генерации (Случайное изображение и Запрос по кнопке)

Этот процесс используется как для **Случайного изображения**, так и для **Запроса по кнопке**. Это многоступенчатый, неблокирующий процесс, разработанный для улучшения пользовательского опыта.

1.  **Триггер**:
    -   **Запрос по кнопке**: Сообщение пользователя совпадает с текстом на кнопке (например, "Get Image ❤️‍🔥") или командой `/photo`. Обрабатывается в `src/telegram/dispatcher.py`.
    -   **Случайное изображение**: Внутри `src/telegram/handlers/messages.py`, в функции `process_regular_message`, проходит случайная проверка, по результатам которой принимается решение об отправке изображения.

2.  **Первичный обработчик (`handle_photo_request`)**:
    -   **Файл**: `src/telegram/handlers/media.py`
    -   Эта функция является точкой входа. Она не подбирает изображение напрямую. Вместо этого она отправляет пользователю временное сообщение (placeholder), например, "Ваша иллюстрация подбирается...", и планирует фоновую задачу для выполнения основной работы. Это предотвращает "зависание" бота.

3.  **Фоновая задача (`generate_and_update_illustration`)**:
    -   **Файл**: `src/telegram/use_cases/generate_illustration_task.py`
    -   Эта функция выполняется в фоновом режиме. Ее основная задача — вызвать основную логику, а затем обновить временное сообщение окончательным подобранным изображением или сообщением об ошибке.

4.  **Основная логика (`get_illustration`)**:
    -   **Файл**: `src/telegram/use_cases/get_illustration.py`
    -   Здесь находится фактическая логика подготовки и выполнения внешнего вызова API для подбора изображения.

5.  **Роль `config_id`**:
    Параметр `config_id` имеет решающее значение для определения того, какой набор изображений доступен для подбора. Логика внутри `get_illustration` следующая:
    -   **`config_id` отсутствует (`None`)**: API получает инструкцию использовать **только изображения по умолчанию** (не связанные с какой-либо конкретной историей).
    -   **`config_id` присутствует**: Система проверяет булевый флаг `include_default_images` в конфигурации истории.
        -   Если `True`, API может использовать изображения **из этой истории И изображения по умолчанию**.
        -   Если `False`, API может использовать изображения **ТОЛЬКО из этой конкретной истории**.

6.  **Внешний вызов API**:
    -   **Сервис-получатель**: `flirtello-chats`
    -   **Файл**: `src/telegram/use_cases/get_illustration.py`
    -   **Эндпоинт**: `/illustrations/get_illustration`
    -   Вызов осуществляется через `LLMServiceAPI` на `roleplay_api_url`. Он отправляет историю последних сообщений в качестве контекста.
    -   **Логика сервиса-получателя**: Сервис `flirtello-chats` **не генерирует новые изображения**. Он выступает в роли "умного поисковика":
        1.  С помощью LLM анализирует контекст чата, чтобы понять, какая сцена описывается.
        2.  Выполняет векторный поиск по своей базе данных, чтобы найти наиболее подходящие, уже существующие изображения.
        3.  Возвращает ID наилучшего найденного изображения.

### 2. Процесс неявной генерации (Текстовый запрос)

Этот процесс используется, когда пользователь просит изображение обычным текстом. **Логика этого процесса кардинально различается в зависимости от наличия `config_id`.**

#### Сценарий 2А: `config_id` ОТСУТСТВУЕТ (прямой вызов)

Когда пользователь находится вне конкретной истории, `backend-service` обращается за подбором картинки напрямую к `context-images-microservice`.

1.  **Триггер**: Пользователь отправляет текстовое сообщение. В `src/telegram/use_cases/get_response_from_character.py` проверка на `config_id` не проходит, и исполнение идет по "старой" ветке логики.
2.  **Основная логика**: Вызывается функция `async_send_message_and_get_response`, которая, по-видимому, инкапсулирует прямой вызов к `context-images-microservice`.
3.  **Внешний вызов API**:
    -   **Сервис-получатель**: `context-images-microservice` (предположительно).
    -   **Эндпоинт**: `/contextual_image` (предположительно).
    -   **Логика**: `backend-service` напрямую спрашивает у `context-images-microservice`, нужно ли отправлять картинку в ответ на это сообщение.

#### Сценарий 2Б: `config_id` ПРИСУТСТВУЕТ (вызов через `flirtello-chats`)

Когда пользователь находится в рамках истории, в процесс включается сервис `flirtello-chats` в качестве оркестратора.

1.  **Триггер**: Пользователь отправляет текстовое сообщение. Проверка на `config_id` в `src/telegram/use_cases/get_response_from_character.py` проходит.
2.  **Внешний вызов API (Шаг 1)**:
    -   **Сервис-получатель**: `flirtello-chats`.
    -   **Эндпоинт**: `/chat/messages`.
3.  **Логика `flirtello-chats`**:
    -   `flirtello-chats` получает запрос и в рамках `GetResponseFromCharacter` use case обращается к LLM за текстовым ответом.
    -   **Внешний вызов API (Шаг 2)**: `flirtello-chats` делает вызов в `context-images-microservice` на эндпоинт `/contextual_image`, чтобы определить, нужно ли прикреплять к ответу изображение.
    -   `flirtello-chats` собирает финальный ответ (текст + опционально ID картинки) и возвращает его в `backend-service`.
